# 阶段7：验证、安装与长期维护

## T25 全流程回归

输入：TEST-PLAN、STATUS、所有已实现功能。
操作：
1. 执行单元、lint、debug构建和设备测试。
2. 按E01/E02/E04/E05跑完整路径，不只单独点每个页面。
3. 检查此前NEEDS_DEVICE_CHECK是否补齐；提醒按E03记录真实边界。
4. 回归问题按严重度修复：数据丢失/错算/无法记录优先于动效。
5. 每个缺陷记录复现与验证，必要时加有意义的防回归测试。
6. 不顺手升级全部依赖或增加功能。
产出：回归记录与剩余问题清单。
验收：无数据丢失、关键计算错误或主流程阻塞；未实测项明确列出。
停止：关键问题没解决不能进入“稳定版发布完成”。
下一项：T26。

## T26 个人签名APK与升级

输入：官方签名文档、E06、现有工程。
操作：
1. 使用稳定release包名和签名；密钥保存在仓库外，记录安全保管方式而非密钥内容。
2. 密钥口令由用户保管，不在聊天、脚本或Git中明文输出。
3. 提供本地签名配置模板与构建说明；不购买开发者账号、不发布商店。
4. 构建release APK，用apkanalyzer/apksigner等实际工具检查包身份/签名。
5. 安装vA并填虚构数据，再构建更高versionCode的vB覆盖安装。
6. 验证数据保留、提醒重排、备份可用；不能卸载重装代替升级测试。
7. 提供本地APK位置及SHA256；不自动上传公开GitHub Release。
产出：个人可长期更新的安装方式与升级证据。
验收：E06全部通过；签名配置不入库；恢复流程可用。
停止：用户尚未保管密钥/实机不可用则明确未完成，不生成“正式已发布”状态。
下一项：T27。

## T27 自用观察

输入：已安装个人版本、已通过备份恢复。
操作：
1. 使用者开始真实记录；真实数据只留设备/用户选择存储，不进公开仓库。
2. 建议观察约7天，记录录入摩擦、提醒实际到达、崩溃和错算。
3. 对照常吃食物与常用动作是否方便，不要求用户每天填复杂调查。
4. 反馈只记录产品问题，公开截图改用虚构复现数据。
5. 修复阻塞并重跑相应测试；不因此扩成商业App。
6. 若用户希望提前结束，记录明确选择与尚未覆盖的观察项。
产出：可复现问题和修复记录。
验收：完成观察或用户明确结束；关键问题处理完毕。
注意：AI不阻塞等待7天、不自动创建提醒任务；以用户后续反馈继续。
下一项：T28。

## T28 v0.1验收与维护交接

输入：TEST-PLAN发布门槛、T27反馈。
操作：
1. 逐项核验发布门槛，区分PASS/NOT_RUN/用户反馈。
2. 编写docs/USER-GUIDE.md：安装、首次设置、记吃/练、查看趋势、提醒限制、备份恢复、更新方式。
3. 编写docs/MAINTENANCE.md：版本更新、数据库迁移、备份兼容、签名保管、恢复和常见问题。
4. 更新README的实际完成状态，不再沿用“仅计划”。
5. 记录版本号与对应提交；按用户授权提交、推送或打本地tag。
6. 远程备份未实现必须明确保留；不可把v0.1当云同步版。
产出：可接续维护的个人工具和使用说明。
验收：所有门槛有证据，后续模型能从STATUS知道真实状态。
下一项：没有必须新增的功能；T29等待用户选择。
